# План: редактор игровых карточек и импорт JSON

## Подход

Добавить самостоятельный раздел **Cards**: ручное создание и редактирование игровых карточек трёх категорий, фильтры и импорт JSON. Авторитетные требования — [facts.md](facts.md); выбранные автоматические проверки — [facts.meta.json](facts.meta.json). AI для содержимого карточек не добавлять.

Игровые карточки — новая сущность, отдельно от `card_types`, которые уже хранят шаблоны оформления. Использовать существующие SQLite, Go API, клиентские API-помощники, формы черновиков и компоненты diff. Сохранение формы происходит по **Save**, импорт — по **Import** после проверки и предпросмотра.

## Контракт данных

Общие поля входной карточки: `faction_id` (ID существующей фракции), `name` (непустая строка после trim), `category` (`combat`, `schema`, `upgrade`). Ответ API дополнительно содержит `id`, `created_at`, `updated_at`.

| Категория | Обязательные поля | Допустимые значения |
| --- | --- | --- |
| combat | `level`, `resource_cost`, `upper_text`, `lower_text`, `shields`, `guns`, `eagles` | уровень 0–3; цена и счётчики — целые числа от 0; оба текста могут быть пустыми |
| schema | `subtype`, `text`, `action` | subtype: `schema`, `tactic`; action: `rotate_clockwise`, `rotate_counterclockwise`, `move_vertical`, `move_horizontal` |
| upgrade | `upgrade_type`, `text` | `deploy`, `advance`, `strategize`, `upgrade` |

`text` может быть пустым. Поля другой категории, неизвестные ключи, `null` вместо обязательного значения, дроби и числовые строки отвергать. Числа должны быть безопасными целыми для JavaScript (не больше 9007199254740991); это ограничение передачи данных, а не правило баланса игры. Не вводить уникальность названий карточек без отдельного требования. Повторный импорт создаёт новые записи.

Формат импорта — объект с единственным полем `cards`, содержащим непустой массив карточек. Например, `faction_id: 1` ниже нужно заменить на ID существующей фракции:

```json
{
  "cards": [
    {
      "faction_id": 1,
      "name": "Огневое превосходство",
      "category": "combat",
      "level": 0,
      "resource_cost": 0,
      "upper_text": "Текст верхнего эффекта",
      "lower_text": "",
      "shields": 1,
      "guns": 2,
      "eagles": 0
    },
    {
      "faction_id": 1,
      "name": "Перегруппировка",
      "category": "schema",
      "subtype": "tactic",
      "text": "Переместите в своём поле.",
      "action": "move_horizontal"
    },
    {
      "faction_id": 1,
      "name": "Подкрепление",
      "category": "upgrade",
      "upgrade_type": "deploy",
      "text": "Текст улучшения"
    }
  ]
}
```

## Порядок реализации

1. **Добавить модель и хранение карточек.**

   Файлы: новые `server/internal/store/cards.go`, `cards_test.go`, миграция `server/internal/store/migrations/0015_cards.up.sql` и парный down-файл; тесты миграций в `db_test.go`. Перед реализацией проверить, что 0015 по-прежнему свободен.

   Одна таблица `cards` с общими полями и nullable-полями категорий, CHECK-ограничениями и внешним ключом на фракцию с запретом удаления используемой фракции. Для API использовать типизированные входы с различением отсутствующего числового поля и нуля. Реализовать List/Get/Create/Update и транзакционный Import. Update полностью заменяет редактируемые значения и очищает поля прежней категории при её смене. Import использует один transaction: ошибка любого INSERT откатывает все записи; не обращаться к отдельному db.Get внутри открытой транзакции при одном соединении.

   Проверка: `cd server && go test ./internal/store`. Покрыть все категории и enum-значения, нулевые и граничные числа, неверные значения, Unicode, обновление/смену категории, фильтры, отсутствие фракции, атомарность импорта, закрытие и повторное открытие файловой БД. Миграцию проверить на временной БД с данными до версии 0015: фракции, шаблоны и существующие записи сохраняются. Факты: categories, faction, combat-*, schema-kind, schema-action, upgrade-*, persistence, language, validation, json-commit, existing.

2. **Добавить API и независимую серверную валидацию.**

   Файлы: новые `server/internal/api/cards.go`, `cards_test.go`; `server/internal/api/router.go`, `factions.go` и тесты удаления фракций.

   Маршруты: `GET /api/cards?faction_id=&category=`, `GET /api/cards/{id}`, `POST /api/cards`, `PUT /api/cards/{id}`, `POST /api/cards/import`. Формы и импорт используют одни правила серверной валидации. Импорт принимает JSON напрямую, без загрузки файла на диск; возвращает созданные карточки и их количество. Ошибки 400 содержат понятное сообщение и список `{index, field, message}` для импортируемых записей; отсутствующая карточка — 404. Проверять неизвестные поля и лишний JSON после основного объекта. Не полагаться на клиентскую проверку существования фракции. Удаление фракции с карточками возвращает 409 с объяснением; фракции без карточек удаляются как раньше.

   Проверка: `cd server && go test ./internal/api`. Проверить create/get/update/filter для всех категорий, malformed JSON, пропущенные поля, неверные типы/enum, отрицательные/дробные/слишком большие числа, неизвестные ключи, чужие поля категории, пустой массив, неизвестную фракцию и отсутствие частичного импорта. Проверить успешный смешанный импорт, сохранение повторного импорта как новых записей, 409 на удаление используемой фракции и прежнее удаление свободной. Факты: validation, json-upload, json-validation, json-commit, existing плюс поля карточек.

3. **Добавить список и ручной редактор Cards.**

   Файлы: новые `web/src/pages/cards/api.ts`, `model.ts`, `validation.ts`, `store.ts`, `CardsPage.tsx`, `CardDialog.tsx` и их тесты; `web/src/App.tsx`, `web/src/components/Sidebar.tsx`. Переиспользовать `Field`, `Dialog`, `ConfirmDialog`, `DiffPanel` и `web/src/lib/draftForm.ts`, не менять поведение старых редакторов.

   Список показывает название, фракцию и категорию; фильтры по фракции и категории работают совместно. Форма показывает только поля выбранной категории. Черновик хранит вводимые числа строками, строгая проверка и преобразование происходят перед Save; пустой числовой ввод не превращается незаметно в 0. При смене категории инициализировать её поля и не отправлять поля прежней. Нет фракций — показать ссылку на Factions и отключить сохранение. После успешного Save обновить список; после ошибки сохранить черновик и показать ошибку. Diff охватывает название, все текстовые поля, фракцию, категорию и параметры.

   Для карточек добавить защиту закрытия, переходов внутри приложения и выхода/перезагрузки страницы. Router создан через `createBrowserRouter` в `main.tsx`; проверить актуальную документацию установленного React Router через ctx7 перед использованием блокировки навигации. Отмена перехода сохраняет форму, подтверждение отбрасывает черновик и выполняет переход. Для закрытия вкладки использовать стандартное предупреждение браузера.

   Проверка: `cd web && npx vitest run src/pages/cards`. UI-тесты с MSW: создание/редактирование каждой категории, сохранение правильных payload, комбинации фильтров, все четыре уровня/действия/апгрейда, diff текстов и чисел, Unicode, смена категории, пустое числовое поле, отсутствие фракций, ошибки Save, отмена/подтверждение закрытия и router-перехода. Проверить обработчик browser-unload автоматически, нативный диалог — вручную. Факты: list, persistence, diff, unsaved, language, validation и category-specific поля.

4. **Добавить загрузку JSON, правила и предпросмотр импорта.**

   Файлы: новые `web/src/pages/cards/ImportCardsDialog.tsx`, `import.ts` и тесты; общие `validation.ts`, `api.ts`, `CardsPage.tsx`. Добавить пример с тремя категориями, доступный для скачивания из UI; рядом показать правила и список существующих фракций с ID.

   Прочитать UTF-8 файл локально, проверить envelope и каждую запись общим клиентским валидатором. Показывать ошибки с номером карточки и полем; до успешной проверки и явного Import не выполнять POST. Предпросмотр показывает количество и список будущих карточек. POST отправляет `{cards: [...]}` на `/api/cards/import`. Во время запроса отключить повторное нажатие; успешный импорт обновляет список, ошибка сохраняет файл/предпросмотр и показывает серверные ошибки. Защищать закрытие/переход при подготовленном несохранённом импорте аналогично форме. Названия и тексты из файла отображать как текст.

   Проверка: `cd web && npx vitest run src/pages/cards`. Проверить синтаксис JSON, поля/диапазоны/enum/неизвестные ключи/фракции, пустой массив, UTF-8, пример для скачивания, предпросмотр без POST, единственный POST только по Import, сохранение состояния при ошибке, обновление списка при успехе. Валидатор UI и API должны проходить одинаковые наборы валидных/невалидных JSON-примеров. Факты: json-upload, json-validation, json-commit, language, validation, unsaved.

5. **Проверить готовую функцию и существующие сценарии.**

   Команды: `make test`; `cd web && npm run build`; `cd web && npm run lint`. Не запускать `make build` ради проверки: он заменяет `server/webdist`; для Go достаточно `cd server && go test ./...` из `make test`.

   В dev-сборке создать и отредактировать карточку каждой категории, посмотреть diff, отменить закрытие и переход, сохранить, перезагрузить и проверить значения. Проверить нативное предупреждение выхода, импорт смешанного JSON и импорт с одной ошибочной записью (ноль сохранённых карточек). Убедиться, что подписи английские, кириллица сохраняется, AI-кнопок для карточек нет, schema-перемещение описано в своём поле и не симулируется. Существующие Factions, Card Types, gallery и batch UI проверить на тестовых данных без оплачиваемых внешних запросов.

   Для каждого факта с `automatedVerification: true` сопоставить конкретный тест в итоговом отчёте; если окружение блокирует проверку, явно указать факт и причину. Факты manual, schema-field, scope проверяются ручным просмотром UI и итогового diff. Приложить итог проверок и оставшиеся ограничения.

## Риски и принятые решения

- Название `upgrade` как четвёртый тип приказа — явный ответ пользователя; не заменять его на Dominate. Schema и tactic — подтипы одной категории.
- JSON-import расширяет старый PRD, где карточный контент не входил в область проекта. Эти принятые facts определяют новую область; существующие artwork-промпты не менять.
- Повторный импорт не идемпотентен: создаёт новые карточки. Не добавлять автоматическое обновление по имени или удаление дублей.
- Фракцию с карточками нельзя удалять: иначе нарушается обязательная привязка. Это узкое изменение существующего Delete, требующее понятного 409 и регрессионного теста.
- Клиент и сервер валидируют независимо; общие JSON-примеры защищают от расхождения правил. Предупреждение browser-unload зависит от браузера, его текст задаёт браузер.

## Условие завершения

Все принятые факты выполнены, выбранные автоматические проверки проходят либо имеют документированный внешний блокер, ручные проверки выполнены. Редактор и атомарный JSON-import работают с сохранёнными данными; существующие сценарии не сломаны. Эта задача setup-goal создаёт пакет цели, а не реализует функцию.
